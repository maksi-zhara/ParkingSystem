# Проектирование защиты от двойного бронирования

Пакет ИСР: **A2** (задача 9). История: **ID-01** (запрет двойного бронирования).
Связанные правила: `../requirements/booking-rules.md`.

## 1. Проблема

При одновременных запросах на одно парковочное место с пересекающимися
интервалами оба запроса могут пройти проверку в приложении до того, как первый
сохранит запись (состояние гонки). Без дополнительной защиты это приводит к двум
активным броням на один интервал.

**Инвариант:** для одного места среди активных броней (статус `RESERVED`) не может
существовать двух пересекающихся интервалов.

## 2. Предикат пересечения

Интервал брони трактуется как полуинтервал `[startsAt, endsAt)`.
Два интервала `A` и `B` пересекаются, если:

```
A.startsAt < B.endsAt  AND  B.startsAt < A.endsAt
```

Проверка нового периода `[reqStart, reqEnd)` для места `S`:

```
startsAt < reqEnd  AND  endsAt > reqStart   (status = RESERVED, spot = S)
```

## 3. Двухуровневая защита

### Уровень 1 — предварительная проверка в приложении

Перед сохранением сервис бронирования проверяет наличие пересекающейся активной
брони. Это даёт ранний, понятный ответ пользователю и разгружает БД.

- создание: поиск пересечений по месту;
- перенос/продление: поиск пересечений по месту **за исключением текущей брони**.

Проверки в приложении недостаточно — между проверкой и вставкой возможна гонка,
поэтому обязателен второй уровень.

### Уровень 2 — ограничение целостности в БД

На таблице броней создаётся **исключающий индекс** (`GiST`) по месту и интервалу:

```sql
create extension if not exists btree_gist;

alter table reservations
    add constraint ex_reservations_spot_reserved_period
        exclude using gist (
            parking_spot_id with =,
            tstzrange(starts_at, ends_at, '[)') with &&
        )
        where (status = 'RESERVED');
```

- `tstzrange(starts_at, ends_at, '[)')` — полуинтервал, согласованный с предикатом;
- `&&` — оператор пересечения диапазонов;
- `where (status = 'RESERVED')` — ограничение действует только на активные брони,
  поэтому отменённые и истёкшие брони не блокируют место.

Расширение `btree_gist` необходимо, чтобы совместить в одном индексе равенство по
`parking_spot_id` (UUID) и пересечение по диапазону времени.

**Почему БД:** ограничение проверяется атомарно на уровне СУБД и не зависит от
гонок между транзакциями — при одновременных вставках успешной окажется только одна.

## 4. Транзакции и обработка конфликта

- Создание и изменение брони выполняются в транзакции (`@Transactional`).
- После сохранения вызывается принудительная синхронизация с БД (`saveAndFlush`),
  чтобы нарушение ограничения проявилось внутри транзакции, а не при коммите.
- Нарушение ограничения приходит как `DataIntegrityViolationException`.
  Сервис распознаёт имя ограничения `ex_reservations_spot_reserved_period`
  (в сообщении / первопричине) и преобразует его в доменное исключение
  `ReservationConflictException`.
- Обработчик ошибок (`RestExceptionHandler`) отображает его в HTTP **409 Conflict**
  с сообщением «Парковочное место уже занято на выбранный период».

Прочие нарушения целостности (не по этому ограничению) не маскируются и
пробрасываются дальше.

## 5. Применение к операциям

| Операция | Проверка приложения | Ограничение БД |
| --- | --- | --- |
| Создание брони | пересечения по месту | да (при вставке) |
| Перенос / продление | пересечения по месту, кроме текущей брони | да (при обновлении интервала) |
| Отмена | — (освобождает интервал) | не мешает: статус ≠ `RESERVED` |
| Истечение | — (перевод в `EXPIRED`) | не мешает: статус ≠ `RESERVED` |

## 6. Критерии приёмки

- Для одного места и пересекающихся интервалов одновременно успешна не более
  одна активная бронь; второй запрос отклонён с кодом `409`.
- Инвариант подтверждён **конкурентным тестом**: параллельные запросы на одно
  место не создают две активные брони.
- Отменённая или истёкшая бронь не блокирует создание новой на тот же интервал.
